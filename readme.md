## سؤال ۱ — merge و rebase

هر دو دستور برای آوردن تغییرات یک شاخه به شاخه‌ی دیگر به کار می‌روند، ولی روش ترکیب تغییرات و شکلی که تاریخچه بعد از آن‌ها پیدا می‌کند کاملاً متفاوت است.

برای مقایسه این وضعیت را در نظر می‌گیرم: شاخه‌ی `feature` از کامیت `B` جدا شده، بعد از آن روی `main` دو کامیت `C` و `D` و روی `feature` دو کامیت `E` و `F` ثبت شده است:

```text
      E---F         feature
     /
A---B---C---D       main
```

### git merge

وقتی روی `main` هستم و `git merge feature` را اجرا می‌کنم، گیت اول نقطه‌ی مشترک دو شاخه (merge base، اینجا `B`) را پیدا می‌کند. بعد سه نسخه را با هم مقایسه می‌کند (`B` به عنوان پایه، `D` و `F` به عنوان دو سر شاخه‌ها) و نتیجه را در یک کامیت جدید به اسم **merge commit** ثبت می‌کند که **دو والد** دارد:

```text
      E---F
     /     \
A---B---C---D---M   main
```

- هیچ‌کدام از کامیت‌های قبلی تغییر نمی‌کنند و هششان همان می‌ماند؛ یعنی تاریخچه همان‌طور که واقعاً اتفاق افتاده حفظ می‌شود.
- اگر `main` بعد از جدا شدن `feature` جلو نرفته باشد، گیت فقط اشاره‌گر `main` را جلو می‌برد (**fast-forward**) و کامیت merge نمی‌سازد؛ مگر اینکه گزینه‌ی `--no-ff` را بدهم.
- اگر conflict پیش بیاید، فقط یک بار و موقع ساختن `M` حل می‌شود.

### git rebase

وقتی روی `feature` هستم و `git rebase main` را اجرا می‌کنم، گیت تغییراتِ کامیت‌های `E` و `F` را برمی‌دارد و آن‌ها را یکی‌یکی روی آخرین کامیت `main` (یعنی `D`) دوباره اعمال می‌کند:

```text
A---B---C---D---E'---F'   feature
```

- `E'` و `F'` کامیت‌های **جدیدی** هستند: محتوای تغییرشان شبیه قبل است، اما والد و در نتیجه هششان فرق می‌کند. پس rebase در واقع **تاریخچه را بازنویسی می‌کند**.
- تاریخچه کاملاً خطی می‌شود و merge بعدی `feature` در `main` به‌صورت fast-forward انجام می‌شود.
- conflict ممکن است برای هر کامیت جداگانه پیش بیاید. در آن صورت فایل را درست می‌کنم، `git add` می‌زنم و با `git rebase --continue` ادامه می‌دهم؛ برای انصراف هم `git rebase --abort` هست.

### جمع‌بندی تفاوت‌ها

| ویژگی | merge | rebase |
|---|---|---|
| نحوه‌ی ترکیب | ادغام سه‌طرفه و ساخت یک کامیت جدید با دو والد | اعمال دوباره‌ی تک‌تک کامیت‌ها روی پایه‌ی جدید |
| شکل تاریخچه | غیرخطی؛ شاخه‌ها و نقطه‌ی ادغام دیده می‌شوند | خطی و مرتب |
| کامیت‌های قبلی | دست‌نخورده می‌مانند | با هش جدید بازسازی می‌شوند |
| حل conflict | یک بار | ممکن است برای هر کامیت جدا لازم شود |
| روی شاخه‌ی مشترک | امن | خطرناک (تاریخچه‌ی بقیه را به هم می‌ریزد) |

### موقعیت مناسب برای merge

وقتی کار یک قابلیت روی شاخه‌ی `feature-login` تمام شده و review شده و حالا باید وارد `main` مشترک تیم شود:

```bash
git switch main
git pull origin main
git merge --no-ff feature-login
git push origin main
```

دلیل انتخاب: `main` شاخه‌ای است که همه‌ی تیم از آن کامیت گرفته‌اند، پس نباید چیزی در آن بازنویسی شود و merge دقیقاً همین ویژگی را دارد. با `--no-ff` هم در تاریخچه مشخص می‌ماند که این چند کامیت با هم یک قابلیت بوده‌اند، و اگر بعداً لازم شد، کل قابلیت با revert کردن همان یک کامیت merge برگردانده می‌شود.

### موقعیت مناسب برای rebase

وقتی روی شاخه‌ی شخصی خودم کار می‌کنم که کس دیگری از آن استفاده نمی‌کند، و در این مدت `main` چند کامیت جلو رفته است. قبل از باز کردن Pull Request شاخه‌ام را به‌روز می‌کنم:

```bash
git switch feature-login
git fetch origin
git rebase origin/main
```

دلیل انتخاب: چون شاخه فقط مال خودم است، بازنویسی تاریخچه‌اش به کسی آسیب نمی‌زند. در عوض کامیت‌های من مرتب روی آخرین نسخه‌ی `main` قرار می‌گیرند، کامیت merge اضافه‌ای مثل «Merge main into feature» ساخته نمی‌شود، conflictها همین‌جا روی شاخه‌ی خودم حل می‌شوند و review کردن PR برای بقیه ساده‌تر است. اگر شاخه را قبلاً push کرده باشم، بعد از rebase باید با `git push --force-with-lease` بفرستم که فقط برای شاخه‌ی شخصی قابل قبول است.

> **قانون کلی:** کامیت‌هایی را که روی شاخه‌ی مشترک push شده‌اند rebase نمی‌کنم؛ rebase برای مرتب کردن کار محلی و شخصی است و merge برای یکپارچه کردن کار در شاخه‌های مشترک.

## سؤال ۲ — انتخاب بخشی از تغییرات (hunk)

### hunk چیست؟

خروجی `git diff` برای هر فایل از یک یا چند **hunk** تشکیل می‌شود. هر hunk یک تکه‌ی پیوسته از تغییرات است، همراه با چند خط اطرافش که تغییر نکرده‌اند (خطوط context، به‌طور پیش‌فرض سه خط) تا معلوم باشد تغییر کجای فایل است. هر hunk با یک سرآیند `@@` شروع می‌شود:

```diff
@@ -10,5 +10,6 @@
 ## Installation
 
-npm install
+npm ci
+npm run build
 
 ## Usage
```

در این سرآیند، `-10,5` یعنی این تکه در نسخه‌ی قبلی از خط ۱۰ شروع می‌شود و ۵ خط است، و `+10,6` یعنی در نسخه‌ی جدید از خط ۱۰ شروع می‌شود و ۶ خط است. خطوطی که با `-` شروع می‌شوند حذف شده‌اند، خطوط `+` اضافه شده‌اند و خطوطی که با فاصله شروع می‌شوند همان context هستند.

### stage کردن تعاملی بخشی از تغییرات

فرض کنید در فایل `app.js` همزمان سه کار کرده‌ام: یک باگ در اعتبارسنجی ایمیل را درست کرده‌ام، چند `console.log` برای دیباگ گذاشته‌ام و یک قابلیت نیمه‌کاره را هم شروع کرده‌ام. می‌خواهم کامیت بعدی فقط رفع باگ باشد.

اول کل تغییرات را نگاه می‌کنم و بعد حالت تعاملی را باز می‌کنم:

```bash
git diff app.js
git add -p app.js        # یا: git add --patch app.js
```

گیت hunkها را یکی‌یکی نشان می‌دهد و برای هر کدام می‌پرسد:

```text
(1/3) Stage this hunk [y,n,q,a,d,s,e,?]?
```

| گزینه | کار |
|:---:|---|
| `y` | این hunk را stage کن |
| `n` | این hunk را stage نکن |
| `s` | hunk را به hunkهای کوچک‌تر بشکن (اگر بین تغییرات خط بدون تغییر باشد) |
| `e` | patch این hunk را دستی در ویرایشگر ویرایش کن |
| `a` | این hunk و همه‌ی hunkهای بعدی همین فایل را stage کن |
| `d` | این hunk و همه‌ی hunkهای بعدی همین فایل را رد کن |
| `q` | خروج؛ hunkهای باقی‌مانده stage نمی‌شوند |
| `?` | نمایش راهنمای همه‌ی گزینه‌ها |

در مثال من، روی hunk مربوط به رفع باگ `y` و روی hunkهای دیباگ و قابلیت نیمه‌کاره `n` می‌زنم. اگر رفع باگ و یک `console.log` در یک hunk افتاده باشند، اول `s` را امتحان می‌کنم تا جدا شوند. اگر خطوط چسبیده به هم باشند و `s` جواب ندهد، با `e` patch را دستی ویرایش می‌کنم: خط `+` ناخواسته را پاک می‌کنم (و اگر خط `-` ناخواسته‌ای بود، علامت آن را به فاصله تبدیل می‌کنم).

بعد قبل از کامیت چک می‌کنم که دقیقاً چه چیزی انتخاب شده:

```bash
git diff --staged     # فقط بخشی که وارد کامیت می‌شود (رفع باگ)
git diff              # بقیه‌ی تغییرات که در working tree مانده‌اند
git commit -m "Fix email validation on login form"
```

اگر hunkی را اشتباهی stage کرده باشم، با `git restore --staged -p app.js` (یا `git reset -p app.js`) می‌توانم همان را تکه‌تکه از staging خارج کنم. دستور `git add -i` هم یک منوی تعاملی دارد که گزینه‌ی `patch` آن همین کار را انجام می‌دهد.

> نکته: `-p` روی فایل‌های tracked کار می‌کند. برای فایل کاملاً جدید اول `git add -N file` (intent to add) می‌زنم تا گیت فایل را بشناسد و بعد `git add -p`.

### فایده برای ساختن کامیت‌های منسجم

- هر کامیت فقط **یک تغییر منطقی** دارد، حتی وقتی چند کار مختلف را همزمان در یک فایل انجام داده‌ام.
- پیام کامیت دقیقاً با محتوایش جور درمی‌آید و review کردنش ساده‌تر است.
- اگر بعداً یک تغییر مشکل‌دار بود، می‌شود فقط همان را revert یا cherry-pick کرد بدون اینکه کارهای دیگر هم برگردند.
- `git bisect` (سؤال ۳) با کامیت‌های کوچک و منسجم دقیق‌تر به منشأ خطا می‌رسد.
- چون هر تغییر را قبل از stage شدن می‌بینم، کد دیباگ یا کار نیمه‌کاره اشتباهی وارد کامیت نمی‌شود.

## سؤال ۳ — یافتن منشأ خطا با bisect

### نحوه‌ی کار

`git bisect` روی تاریخچه **جست‌وجوی دودویی** انجام می‌دهد. به گیت یک کامیت سالم (good) و یک کامیت معیوب (bad) می‌دهم؛ گیت کامیت وسط این بازه را checkout می‌کند و من فقط می‌گویم خطا در آن هست یا نه. با هر جواب نصف بازه کنار گذاشته می‌شود، پس برای n کامیت حدوداً log₂(n) بار تست لازم است؛ مثلاً برای ۱۰۰۰ کامیت حدود ۱۰ مرحله.

### مراحل

**۱. شروع و مشخص کردن دو سر بازه**

```bash
git bisect start
git bisect bad                  # کامیت فعلی (HEAD) خطا دارد
git bisect good v1.4.0          # این نسخه سالم بوده (تگ یا هش کامیت)
```

(معادل کوتاه: `git bisect start HEAD v1.4.0`)

گیت پیامی شبیه این می‌دهد و کامیت وسط را در حالت detached HEAD checkout می‌کند:

```text
Bisecting: 64 revisions left to test after this (roughly 6 steps)
```

**۲. تست هر کامیت و اعلام نتیجه**

برنامه را اجرا یا تست می‌کنم و نتیجه را به گیت می‌گویم:

```bash
git bisect good     # در این کامیت خطا وجود ندارد
git bisect bad      # در این کامیت خطا وجود دارد
git bisect skip     # این کامیت قابل تست نیست (مثلاً build نمی‌شود)
```

گیت بعد از هر جواب کامیت وسطِ بازه‌ی باقی‌مانده را checkout می‌کند.

**۳. پایان جست‌وجو**

وقتی بازه به یک کامیت برسد، گیت آن را اعلام می‌کند:

```text
3f9c2a1e... is the first bad commit
```

تغییرات آن کامیت را بررسی می‌کنم و بعد به وضعیت قبل برمی‌گردم:

```bash
git show 3f9c2a1
git bisect log       # (اختیاری) خلاصه‌ی مراحلی که طی شد
git bisect reset     # بازگشت به شاخه و کامیتی که قبل از شروع روی آن بودم
```

**خودکارسازی:** اگر خطا با یک اسکریپت یا تست قابل تشخیص باشد، کل جست‌وجو را خود گیت انجام می‌دهد:

```bash
git bisect start HEAD v1.4.0
git bisect run ./check_total.sh
```

قرارداد کد خروج اسکریپت: `0` یعنی good، `125` یعنی skip، و بقیه‌ی مقادیر ۱ تا ۱۲۷ یعنی bad.

### مثال

در فروشگاه اینترنتی پروژه، جمع مبلغ سبد خرید وقتی کد تخفیف وارد می‌شود اشتباه حساب می‌شود. می‌دانم در نسخه‌ی `v1.4.0` که دو هفته پیش منتشر شده درست کار می‌کرده و از آن موقع حدود ۱۳۰ کامیت اضافه شده. یک تست کوچک می‌نویسم که مبلغ یک سبد نمونه را با تخفیف حساب کند و با `git bisect run` اجرا می‌کنم. گیت بعد از حدود ۷ مرحله کامیتی را پیدا می‌کند که در آن ترتیب اعمال تخفیف و مالیات عوض شده؛ diff همان کامیت چند خط بیشتر نیست و علت خطا سریع پیدا می‌شود.

### چرا مفید است؟

- لازم نیست حدس بزنم خطا در کدام بخش کد است؛ روش سیستماتیک است و حتی بدون شناخت کد جواب می‌دهد.
- تعداد مراحل لگاریتمی است؛ بررسی صدها کامیت با چند تست تمام می‌شود.
- خروجی یک کامیت مشخص است: diff کوچک، پیام کامیت و نویسنده‌اش معلوم است، پس هم علت خطا و هم هدف اصلی آن تغییر روشن می‌شود و رفعش ساده‌تر است.
- با `bisect run` کل کار خودکار و قابل تکرار می‌شود.

## سؤال ۴ — بررسی تغییرات پیش از کامیت

در این وضعیت از فایل `README.md` سه نسخه وجود دارد:

| نسخه | محتوا |
|---|---|
| آخرین کامیت (HEAD) | نسخه‌ی قبلی فایل |
| ناحیه‌ی staging (index) | HEAD + بخشی از تغییرات که add کرده‌ام (اسمش را **الف** می‌گذارم) |
| working tree | الف + ویرایش‌هایی که بعد از add انجام داده‌ام (اسمش را **ب** می‌گذارم) |

### ۴-۱. دستورهای بررسی

**وضعیت کلی مخزن:**

```bash
git status
```

```text
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   README.md

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   README.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        tmp/
```

همان‌طور که می‌بینید `README.md` در هر دو بخش آمده و این کاملاً طبیعی است. در خروجی کوتاه (`git status -s`) هم به شکل `MM README.md` و `?? tmp/` دیده می‌شود؛ ستون اول وضعیت index نسبت به HEAD و ستون دوم وضعیت working tree نسبت به index است.

**تغییراتی که هنوز وارد staging نشده‌اند:**

```bash
git diff
```

working tree را با index مقایسه می‌کند؛ یعنی فقط بخش **ب** را نشان می‌دهد.

**تغییرات آماده‌ی کامیت:**

```bash
git diff --staged       # معادل: git diff --cached
```

index را با HEAD مقایسه می‌کند؛ یعنی فقط بخش **الف** را نشان می‌دهد که در کامیت بعدی قرار می‌گیرد.

(برای دیدن همه‌ی تغییرات نسبت به آخرین کامیت، یعنی الف و ب با هم، از `git diff HEAD` استفاده می‌شود.)

**تفاوت این دو دسته:** تغییرات staged چیزی است که من صراحتاً برای کامیت بعدی انتخاب کرده‌ام و گیت یک نسخه از آن را در index نگه داشته. تغییرات unstaged فقط روی دیسک من هستند؛ گیت از آن‌ها خبر دارد ولی تا وقتی دوباره `git add` نزنم، وارد کامیت نمی‌شوند.

### ۴-۲. نتیجه‌ی کامیت معمولی

```bash
git commit -m "Update installation section"
```

این کامیت **فقط بخش الف** را شامل می‌شود و **بخش ب** به‌صورت تغییر unstaged در working tree باقی می‌ماند.

دلیل: `git add` همان لحظه یک کپی (snapshot) از محتوای فایل را در index ذخیره می‌کند؛ اشاره‌ای به خود فایل نگه نمی‌دارد. `git commit` هم کامیت را فقط از روی index می‌سازد و به working tree نگاه نمی‌کند. پس ویرایش‌هایی که بعد از add انجام شده‌اند در index نیستند و وارد کامیت نمی‌شوند.

بعد از کامیت، `git diff --staged` خالی است و `git diff` همچنان بخش ب را نشان می‌دهد. اگر می‌خواستم ب هم در همین کامیت باشد، باید قبل از کامیت دوباره `git add README.md` می‌زدم. پوشه‌ی `tmp/` هم چون untracked است و هیچ‌وقت add نشده، در کامیت نیست.

### ۴-۳. نادیده گرفتن پوشه‌ی tmp

در ریشه‌ی مخزن فایل `.gitignore` را می‌سازم (یا ویرایش می‌کنم) و این خط را اضافه می‌کنم:

```gitignore
# temporary files
/tmp/
```

الگوی `/tmp/` فقط پوشه‌ی `tmp` در ریشه‌ی مخزن را شامل می‌شود؛ اگر `tmp/` بدون اسلش اول بنویسم، هر پوشه‌ای با این اسم در هر جای پروژه نادیده گرفته می‌شود. بعد خود `.gitignore` را کامیت می‌کنم تا این تنظیم برای همه‌ی اعضای تیم اعمال شود:

```bash
git add .gitignore
git commit -m "Ignore temporary files in tmp/"
git status                              # دیگر tmp/ در Untracked files نیست
git check-ignore -v tmp/cache.log       # نشان می‌دهد کدام قانون فایل را ignore کرده
```

(اگر بخواهم این قانون فقط برای خودم باشد و با تیم به اشتراک گذاشته نشود، به جای `.gitignore` آن را در `.git/info/exclude` می‌نویسم.)

**آیا برای فایلی که قبلاً tracked شده کافی است؟ خیر.** `.gitignore` فقط روی فایل‌های untracked اثر دارد. فایلی که در index هست همچنان دنبال می‌شود و تغییراتش در `git status` می‌آید، حتی اگر با الگوهای `.gitignore` جور باشد. برای این فایل‌ها اول باید آن‌ها را از index حذف کنم:

```bash
git rm --cached tmp/old.log      # برای کل پوشه: git rm -r --cached tmp/
git commit -m "Stop tracking files in tmp/"
```

گزینه‌ی `--cached` فایل را فقط از index برمی‌دارد و خود فایل روی دیسک می‌ماند؛ از این به بعد چون untracked است، `.gitignore` روی آن اثر می‌کند. دو نکته: فایل در کامیت‌های قدیمی همچنان در تاریخچه هست (اگر اطلاعات حساس بوده، این کار کافی نیست)، و هم‌تیمی‌ها وقتی این کامیت را pull کنند، آن فایل از working tree آن‌ها حذف می‌شود.

## سؤال ۵ — رفع merge conflict در کار گروهی

### ۵-۱. علت conflict

گیت برای merge از ادغام سه‌طرفه استفاده می‌کند: نسخه‌ی کامیت مشترک (base)، نسخه‌ی `main` و نسخه‌ی `feature-description`. برای هر قسمت از فایل، اگر فقط یکی از دو طرف آن را نسبت به base تغییر داده باشد، گیت همان تغییر را برمی‌دارد. اما اینجا **هر دو طرف یک خط مشخص را نسبت به base به دو متن متفاوت تغییر داده‌اند** و گیت راهی ندارد بفهمد کدام درست است یا چطور باید ترکیب شوند؛ این یک تصمیم معنایی است که باید انسان بگیرد، پس merge را متوقف می‌کند و conflict گزارش می‌دهد.

**آیا هر تغییری که دو نفر در یک فایل بدهند conflict ایجاد می‌کند؟ خیر.** اگر تغییرات در قسمت‌های جدا از هم فایل باشند (هم‌پوشانی نداشته باشند و به هم نچسبند)، گیت هر دو را خودکار ادغام می‌کند. اگر هر دو نفر دقیقاً یک تغییر یکسان داده باشند هم conflict پیش نمی‌آید. conflict وقتی رخ می‌دهد که تغییرات روی خطوط یکسان یا خطوط مجاور باشند و با هم فرق کنند. البته ادغام خودکار بدون conflict هم تضمین نمی‌کند نتیجه از نظر منطقی درست باشد، پس بعد از merge بررسی و تست لازم است.

### ۵-۲. شناسایی فایل‌ها و نسخه‌ها

```bash
git status
```

```text
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   README.md
```

فایل‌های دارای conflict زیر **Unmerged paths** با برچسب `both modified` می‌آیند. برای گرفتن فقط فهرست آن‌ها:

```bash
git diff --name-only --diff-filter=U
```

داخل فایل، گیت هر دو نسخه را با **conflict marker** کنار هم قرار می‌دهد:

```text
<<<<<<< HEAD
A simple service for managing a small library.
=======
This project provides a REST API for adding and searching books.
>>>>>>> feature-description
```

| marker | نقش |
|---|---|
| `<<<<<<< HEAD` | شروع ناحیه‌ی conflict؛ از اینجا تا جداکننده نسخه‌ی شاخه‌ی فعلی است (ours، اینجا `main`) |
| `=======` | جداکننده‌ی دو نسخه |
| `>>>>>>> feature-description` | پایان ناحیه؛ بخش بین جداکننده و این خط نسخه‌ی شاخه‌ای است که merge می‌شود (theirs) |

این markerها دو کار می‌کنند: هر دو نسخه را دقیقاً جایی که اختلاف دارند نشان می‌دهند، و فایل را عمداً «خراب» نگه می‌دارند تا اشتباهاً حل‌شده فرض نشود.

اگر `git config --global merge.conflictStyle zdiff3` (یا `diff3`) تنظیم شده باشد، یک بخش `|||||||` هم با متن base اضافه می‌شود که نشان می‌دهد هر طرف دقیقاً چه چیزی را عوض کرده. سه نسخه را جداگانه هم می‌شود دید:

```bash
git show :1:README.md    # نسخه‌ی base (کامیت مشترک)
git show :2:README.md    # نسخه‌ی ours (main)
git show :3:README.md    # نسخه‌ی theirs (feature-description)
```

### ۵-۳. مراحل رفع conflict با حفظ هر دو تغییر

**۱. اجرای merge و دیدن conflict**

```bash
git switch main
git merge feature-description
```

```text
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

**۲. پیدا کردن فایل‌ها:** با `git status` (بالاتر توضیح دادم).

**۳. ویرایش فایل:** `README.md` را باز می‌کنم و به جای انتخاب یکی از دو نسخه، متنی می‌نویسم که اطلاعات هر دو را داشته باشد؛ اگر لازم باشد با هم‌تیمی‌ام روی متن نهایی هماهنگ می‌کنم. سپس هر سه خط marker را پاک می‌کنم:

```text
A simple service for managing a small library, providing a REST API for adding and searching books.
```

**۴. اطمینان از اینکه markerی باقی نمانده:**

```bash
grep -nE '^(<<<<<<<|=======|>>>>>>>)( |$)' README.md    # نباید خروجی‌ای داشته باشد
git diff --check                                          # markerهای جامانده را گزارش می‌کند
```

این بررسی را **قبل از** `git add` انجام می‌دهم، چون `git add` محتوای فایل را چک نمی‌کند و فایلی که هنوز marker دارد را هم بدون اعتراض «حل‌شده» علامت می‌زند. (در Markdown یک خط از `=` زیر عنوان هم معتبر است، پس اگر grep چنین خطی را نشان داد، بررسی می‌کنم که واقعاً marker باشد.) فایل را یک بار هم کامل می‌خوانم که نتیجه معنی‌دار باشد.

**۵. علامت‌گذاری به‌عنوان حل‌شده:**

```bash
git add README.md
git status        # All conflicts fixed but you are still merging.
```

**۶. تکمیل merge:**

```bash
git commit        # پیام پیش‌فرض: Merge branch 'feature-description'
# یا معادل آن:
git merge --continue
```

**۷. بررسی نهایی و push:**

```bash
git log --oneline --graph -5    # کامیت merge با دو والد دیده می‌شود
git push origin main
```

### ۵-۴. لغو merge

```bash
git merge --abort
```

این دستور merge نیمه‌کاره را لغو می‌کند و index و working tree را به وضعیت قبل از `git merge` برمی‌گرداند؛ `main` روی همان کامیت قبلی می‌ماند و شاخه‌ی `feature-description` هم دست نمی‌خورد. چون طبق صورت سؤال قبل از merge working tree تمیز بوده، بازگشت کامل و بدون ریسک انجام می‌شود (اگر قبل از merge تغییرات ثبت‌نشده وجود داشت، ممکن بود بازگرداندنشان کامل نباشد). معادل قدیمی‌تر آن `git reset --merge` است.

## سؤال ۶ — انتخاب روش مناسب برای بازگرداندن تغییرات

### ۶-۱. دور ریختن تغییرات unstaged یک فایل

```bash
git diff notes.txt          # اول مطمئن می‌شوم چه چیزی را دور می‌ریزم
git restore notes.txt       # معادل قدیمی: git checkout -- notes.txt
```

`git restore` بدون گزینه، نسخه‌ی فایل را از index برمی‌دارد و روی working tree می‌نویسد. چون اینجا index با آخرین کامیت یکسان است، فایل دقیقاً به نسخه‌ی آخرین کامیت برمی‌گردد.

- **working tree:** فقط تغییرات `notes.txt` حذف می‌شوند؛ چون مسیر فایل را مشخص کرده‌ام، فایل‌های دیگر دست نمی‌خورند.
- **staging:** تغییری نمی‌کند.
- **تاریخچه:** تغییری نمی‌کند.

> این کار برگشت‌ناپذیر است، چون این تغییرات هیچ‌وقت add یا کامیت نشده‌اند و گیت نسخه‌ای از آن‌ها ندارد. اگر مطمئن نباشم، به جای آن از `git stash push -- notes.txt` استفاده می‌کنم تا تغییرات کنار گذاشته شوند ولی از بین نروند.

### ۶-۲. خارج کردن فایل از staging با حفظ ویرایش‌ها

```bash
git restore --staged notes.txt     # معادل قدیمی: git reset HEAD notes.txt
```

با گزینه‌ی `--staged`، گیت نسخه‌ی `notes.txt` را در index به نسخه‌ی HEAD برمی‌گرداند و به working tree کاری ندارد.

- **working tree:** بدون تغییر؛ ویرایش‌های من سر جایشان هستند.
- **staging:** `notes.txt` دوباره با آخرین کامیت یکسان می‌شود، یعنی دیگر چیزی از آن برای کامیت آماده نیست.
- **تاریخچه:** تغییری نمی‌کند.

بعد از این دستور، `git status` فایل را زیر **Changes not staged for commit** نشان می‌دهد. اینجا نباید از `git reset --hard` استفاده کرد، چون ویرایش‌های working tree را هم پاک می‌کند.

### ۶-۳. بازگرداندن کامیت push‌شده روی main مشترک

روش مناسب **`git revert`** است:

```bash
git switch main
git pull origin main
git log --oneline            # پیدا کردن هش کامیت اشتباه، مثلاً a1b2c3d
git show a1b2c3d             # اطمینان از اینکه کامیت درستی را انتخاب کرده‌ام
git revert a1b2c3d           # با --no-edit پیام پیش‌فرض بدون باز شدن ویرایشگر ثبت می‌شود
git push origin main
```

`git revert` کامیت اشتباه را حذف نمی‌کند؛ یک **کامیت جدید** می‌سازد که دقیقاً عکس تغییرات آن را اعمال می‌کند (پیامش به شکل `Revert "..."` است و هش کامیت اصلی هم در آن ذکر می‌شود).

- **تاریخچه:** یک کامیت جدید به انتهای `main` اضافه می‌شود؛ هیچ کامیتی حذف یا بازنویسی نمی‌شود.
- **working tree و staging:** به وضعیتی می‌رسند که اثر آن کامیت در آن نیست، و چون نتیجه بلافاصله کامیت می‌شود، بعد از revert هر دو تمیز هستند.
- هم‌تیمی‌ها فقط یک `git pull` معمولی می‌زنند و تغییر جدید را می‌گیرند.

**چرا حذف کامیت و force push مناسب نیست؟** اگر با `git reset --hard HEAD~1` کامیت را حذف کنم و با `git push --force` بفرستم:

- تاریخچه‌ی شاخه‌ای که همه از آن کامیت گرفته‌اند بازنویسی می‌شود. هم‌تیمی‌ها هنوز `a1b2c3d` را در `main` محلی خودشان دارند، شاخه‌شان با remote واگرا می‌شود و با اولین pull یا push معمولی، همان کامیت اشتباه دوباره برمی‌گردد.
- اگر کسی در این فاصله کامیت جدیدی push کرده باشد، force push کار او را هم از remote پاک می‌کند.
- هیچ ردی از اینکه چه اشتباهی رخ داد و چطور اصلاح شد باقی نمی‌ماند.
- در بیشتر تیم‌ها `main` به‌صورت protected تنظیم شده و force push روی آن اصلاً مجاز نیست.

در مقابل، revert امن، شفاف و قابل پیگیری است و حتی خودش برگشت‌پذیر است (اگر لازم شد، کامیت revert را revert می‌کنم).

### جمع‌بندی سؤال ۶

| موقعیت | دستور | working tree | staging | تاریخچه |
|:---:|---|---|---|---|
| ۱ | `git restore notes.txt` | تغییرات `notes.txt` دور ریخته می‌شوند | بدون تغییر | بدون تغییر |
| ۲ | `git restore --staged notes.txt` | بدون تغییر (ویرایش‌ها حفظ می‌شوند) | `notes.txt` به نسخه‌ی HEAD برمی‌گردد | بدون تغییر |
| ۳ | `git revert a1b2c3d` | اثر کامیت اشتباه برداشته می‌شود | هماهنگ با کامیت جدید | یک کامیت جدید اضافه می‌شود؛ چیزی حذف نمی‌شود |
